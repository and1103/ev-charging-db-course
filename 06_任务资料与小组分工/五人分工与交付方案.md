# 五人分工与交付方案

第二版路径整合：2026-11-16；原分工编制：2026-11-14。依据本地任务书、个人/小组报告模板、评分标准和当前实现。成员A—E为五个人的临时代号，可换为真实姓名；本方案用于后续学习、维护、复核和报告分工，不据此认定既有代码由五人分别编写。

本方案是可调整的初版，作为当前分工建议；历史方案中的职责描述以本版结合实际实现的边界为准。

## 一、结论与B目录问题

**可以按A—E五条主线分给五个人。** 每人主责一条业务线，并完成该线完整的需求、数据库设计、实现、测试、个人报告及答辩。共享后端和数据库中的交叉业务需要明确维护人和协作人。

原B第二目录“充电估算与到站排队”只有一份422字节的跨线说明，未包含独立DDL、图或业务代码。费用估算实际在B/充电订单与计费/03_schema.sql；排队、叫号、留枪在A/充电估算与到站排队/04_queue.sql。旧说明还提到当前不存在的tariff_slices函数。

现已归档旧说明，去掉重复空目录，补全[B主模块设计与协作说明](../03_需求与设计/业务分线与图件/B_充电订单与计费/充电订单与计费/模块设计.md)。B的8张业务表保留，代码统一在01_平台工程，SQL在02_数据库脚本，PNG在03_需求与设计的B模块；数据库结构和已部署例程无需为目录说明调整。图中Q仅表示排队子分区，归A负责，六套业务图不代表六位成员。

|---|---|---:|---|---|---|
| A | 场站与设施、到站排队 | 9 | 桩枪层级与功率、验收/状态历史、取号叫号、留枪超时及占枪竞争 | 统一命名与DDL依赖、全局模型整合、提交清单；各线负责人仍审核自己的模型 | 资产校验→取号→叫号→留枪→扫码转单 |

工作量按业务复杂度、跨线依赖和验收责任分配。B的8表包含收费和并发控制，E的10表包含较多冻结/金额约束；C虽6表，采集、调度、分区、故障闭环及恢复演练需要单独投入。公共任务只做协调与整合，不能把其他成员的工作转交组长或C。

适配建议：A适合SQL基础及组织能力较强的成员；B适合事务和计算逻辑较强者；C适合测试、数据和运行环境；D适合接口、权限及用户流程；E适合耐心核对金额与异常状态者。按真实能力替换姓名即可；若投入失衡，先调整汇总/演练职责，保持实体和金额规则的主责稳定。

## 三、每人必须交付的完整任务包

每人都要经历“需求分析→概念设计→逻辑设计→物理设计→建库建表→后端/持久层→测试与报告”，不能只负责画图、只写代码或只写报告。

| 阶段 | 每人的具体产物与完成方式 |
|---|---|
| 需求分析 | 本线参与者、用例、用例图、鲁棒图、数据项、状态与异常规则；列出需要其他线输入/输出的接口 |
| 概念设计 | 本线Chen E-R图；解释实体、主标识、联系、1/N及可选性；审核全局UML涉及本线的部分 |
| 逻辑设计 | 本线关系模式、主外键、候选键及函数依赖；说明规范化分解和受控物理冗余，不能笼统宣称全部物理表严格3NF |
| 物理设计 | 字段类型/精度/单位、NULL/default/CHECK、索引及写入成本；每人至少1项真实索引方案，全组合计至少5项安排 |
| SQL与高级对象 | 3个业务问题，每题2种等价SQL，共6条；至少选1题明确涉及3张及以上基础表，视图写法须展开说明依赖；至少3视图、1存储过程、1触发器 |
| 实现与样例 | 本线DDL、DAO/查询服务、参数化访问、合理CRUD/分页/批量；每张主责业务表至少20条合成数据，涵盖正常与异常 |
| 验证 | 本线结果预期、实测、边界、回滚、权限及相关并发测试；提供SQL执行计划和改进解释，不把小样本耗时当作大规模性能结论 |
| 报告和答辩 | 本线小组报告章节、完整个人报告及PDF、本人PPT内容、约50—55秒演示发言；全员合并录像按任务书时长核对 |

| B | 8 | 3 | 8 | 6 | 10 |

## 五、跨线交接与共同修改规则

| 事项 | 维护主责 | 协作人和交接内容 |
|---|---|---|
| 估算费用 | B | A提供枪与可用性、D提供本人车辆与车队卡；报价不取号、不占枪、不冻结资金，排队等待不计入报价 |
| 排队与扫码开单 | A维护04中的open_charge入口 | B审核订单/预授权规则，D审核本人车辆和额度；失败整体回滚，不遗留占枪或冻结 |
| 计量及断连 | B维护订单meter_sample和核价 | C维护采集接入和设备异常，交付时间/读数质量及最后可信时间，禁止把桩总电量平均成枪电量 |
| 钱包/卡与优惠核销 | D维护账户、卡、流水、券 | B维护订单中的冻结快照、付款和退款；修改任何一侧都由双方核对余额、冻结和账单 |
| 消费与企业/运营商财务 | E维护结算及实际票据 | B交付成功收退款和历史金额；D维护发票申请及车队展示v_fleet_month，E核对其财务公式；不把授信账单当现金已付 |
| 设备状态恢复 | C维护故障工单和复核条件 | A维护资产与枪状态规则，B审核活动订单如何结束或进入复核 |
| 登录、权限和部署授权 | D维护账号/认证/隐私业务 | A维护09数据库角色脚本及部署授权范围，各线维护本人/场站/运营商等权限过滤 |
| 全局材料与演练 | A整合模型/提交，C整合测试/恢复 | 每人提供本线内容及证据并修复本人缺陷；B/E负责恢复后的金额核验 |

物理文件位置不总等于某个人独占：open_charge在A04，但同时写B订单；B的付款过程会写D钱包流水。采用“一个入口维护人＋涉及规则共同评审”，避免为了分工复制函数、重复建表或把同一金额逻辑各写一套。

## 六、实施顺序与阶段验收

1. 五人先认领主责与能力范围，对照本线图、SQL和接口解释现有实现；A汇总命名、状态和金额字段，B/D/E先统一付款退款口径。
2. 各人完成本线需求至物理设计，使用现有字典/PNG作为可修订基础，记录实际修改理由；图和代码变更由主责同步。
3. 按当前deploy.py依赖顺序集成，保持9个迁移文件的真实顺序，不按A→B→C→D→E字母顺序直接建表。每人负责本线数据和正反例，C提供统一验收入口。
4. 先验本线，再验A/B/D交易链、A/B/C故障链、B/D/E财务链；C汇总失败项，责任人修复。备份恢复在隔离库进行，不覆盖展示库。
5. 各人写真实个人报告；A整合小组报告与PPT，C整合录像素材，其余成员提供本人内容并共同复核。成员姓名、贡献、Git记录、会议及答辩反馈均按实际发生填写。

第二版已采用Flask电脑版网页，并将前后端及数据库资料合并。最终报告整编、个人PDF、PPT、全员发言录像和真实协作记录仍需后续完成；已有测试结论见后端验收记录。
