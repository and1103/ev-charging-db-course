# MySQL 备份恢复策略与实测

2026-11-14 更新。采用 MySQL 8.4 的全量逻辑备份与连续 binlog 归档；早期方案中的 SQL Server 差异备份术语不适用于当前实现。本项目没有部署自动调度，以下周期是设计方案。

| 项目 | 设计 |
|---|---|
| 全量周期 | 每日02:00，使用 mysqldump --single-transaction --routines --triggers --events --source-data=2 --set-gtid-purged=OFF --no-tablespaces |
| 增量周期 | 最长15分钟归档一次已封口binlog，必要时先滚动日志；保留连续文件和起止坐标，不跳文件 |
| 留存 | 至少7天全量与配套binlog；归档成功前不清理所需日志；重要演示节点另留全量 |
| RPO目标 | 不超过15分钟；依赖归档周期、连续性及校验成功，尚未通过故障演练证明 |
| RTO目标 | 不超过30分钟；以恢复到可查询、金额与对象校验完成为终点，不能将启动实例视为完成 |
| 恢复顺序 | 新隔离库/实例恢复全量，检查备份坐标；如需时间点恢复，再按连续日志重放到目标位置，核验数据后切换 |
| 敏感密钥 | PII密钥需与SQL备份分开加密保管。本机配置用当前Windows用户DPAPI保护；单独SQL文件不包含密钥，跨机器恢复需要事先准备授权密钥备份 |

增量归档使用 binlog，不是 SQL Server 的“差异备份”。单机同盘副本用于课程演练；异地副本与周期归档均尚未执行。RPO/RTO是课程设计目标，不是已经达到的连续运维承诺。

## 历史已执行的全量恢复（2026-11-14）

用 [backup_validate.py](工具/backup_validate.py) 调用安装目录中的 MySQL 8.4 原生 mysqldump/mysql，仅备份 charge_course_20261114。备份记录文件和位置，恢复到新库 charge_course_restore_20261114_final，不覆盖主课设库、验证库及原实验库。

最终实测：

- 全量文件375852字节，备份0.467秒。
- binlog为ROW，坐标YUKINO-AND-bin.000002:2389829。
- 恢复及核验1.974秒；这是当前小样本、本机、全量恢复的测量值。
- 44张业务表及部署控制表，所有行数与完整行内容SHA-256一致；19视图、40例程、54触发器名称集合一致。
- 全部视图可查询，恢复视图没有错误引用原课设库。
- 原始备份保留；恢复时仅改SQL标识符中的库名，不改字符串数据。例程创建参数在finally中恢复原值。

最终备份SQL、恢复验证JSON保留时间、坐标、SHA-256和逐表核验。

## 演练方法与尚未验证范围

周期性演练应选一份全量和随后的连续binlog，恢复到指定订单/付款发生后的目标位置，核验订单费用、支付退款、钱包冻结及流水、结算分成、票据额度和对象数量，再记录实际RPO/RTO。需要另测授权密钥恢复后能否解密合成手机号/车牌，不用真实个人信息做演练。

本次已执行全量恢复；未执行binlog时间点重放、周期归档任务、异机密钥恢复或生产规模恢复。因此不把保存坐标或代码中存在mysqlbinlog方案称作已完成PITR。
